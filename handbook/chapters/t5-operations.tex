\chapter{Operations}
\label{ch:operations}

How to set up the server side (accounts, nginx, databases, the userbots maubot) is
described step by step in \file{server/docs/admin-bot-setup.md} in the \file{matrix-unibas}
repository. This chapter covers running the bot.

Changes to the signup rate limits take effect after a restart of the instance.

\section{Startup check}

On every start (and config change) the bot checks its environment and posts the result to
the audit room:

\begin{center}
\small
\begin{tabularx}{\textwidth}{@{}llL@{}}
\toprule
\textbf{Check} & \textbf{If it fails} & \textbf{Meaning} \\
\midrule
\cmd{admin} & commands refused & the bot account has Synapse's server-admin flag \\
\cmd{ratelimit} & warning & the bot could lift its own rate limit \\
\cmd{audit_room} & warning & the audit room is configured and the bot is in it \\
\cmd{postgres} & warning & plugin data is in PostgreSQL (and so in the backup), not SQLite \\
\cmd{userbots} & \cmd{!bot}, \cmd{!admin bots} refused & professor bots enabled, reachable, and \emph{not} this maubot \\
\bottomrule
\end{tabularx}
\end{center}

Users who hit a refused command are told that a server check failed and to contact an admin.

\section{Logs and slow replies}
\label{sec:timing}

The plugin logs under \cmd{maubot.adminbot.*}. Every command produces one INFO line:

\begin{codefile}[maubot log]
!help from @prof:matrix.dmi.unibas.ch: reached the bot 18734 ms after it was sent, handled in 412 ms
\end{codefile}

\begin{itemize}
  \item \textbf{\enquote{reached the bot} is large}: the delay happens before the plugin runs,
        in Synapse's delivery through \cmd{/sync}, the bot's sync loop, or decryption. The
        \robot{} reaction then also arrives late. Look at Synapse's logs for slow \cmd{/sync}
        requests of \cmd{@adminbot}, at \cmd{mau.client.crypto} warnings in the maubot log,
        and at the server load.
  \item \textbf{\enquote{handled in} is large}: the command itself is slow. Most handlers make a
        few requests to Synapse and some database queries; bulk work runs later as a job.
  \item Rate limiting causes errors (\cmd{M_LIMIT_EXCEEDED}), not delays.
\end{itemize}

\begin{codefile}[terminal on the server]
docker logs matrix-maubot 2>&1 | grep "reached the bot"
\end{codefile}

\section{Releases}

\begin{enumerate}
  \item Raise \cmd{version} in \file{maubot.yaml}.
  \item Run the tests (\cmd{.venv/bin/pytest}); optionally try it against the local dev stack
        (\file{dev/setup.sh}, see \file{README.md}).
  \item Build: \cmd{mbc build} creates \file{ch.unibas.dmi.marvin.adminbot-v<version>.mbp}.
  \item Upload it on the test node in the maubot UI and run the checklist from
        \file{README.md} (encryption, files, signup page, restart during a job).
  \item Upload the same file on production.
\end{enumerate}

\section{Changing the bot}

\begin{itemize}
  \item A command is a method with the \cmd{@command(name, sub, usage=..., role=...)} decorator
        in a \cmd{CommandGroup} class in \file{commands/}. The router finds it automatically.
  \item Every command needs a one-line \cmd{usage.*} text and a detailed \cmd{help.*} text in
        \file{strings/en.py}; a test fails otherwise. Handlers contain no literal text.
  \item Every reply should say what happened, why, and what to do next. Errors are raised
        with a strings key, as \cmd{ValidationError} (bad input), \cmd{NotFound} or
        \cmd{Forbidden}.
  \item Bulk work goes through \cmd{propose()} and a job kind registered with
        \cmd{bot.jobs.register(..., done_hint=...)}.
  \item Update this handbook (\file{handbook/chapters/}) when a command changes;
        \cmd{make} in \file{handbook/} builds both versions.
\end{itemize}
